## Proposal

### Please re-state the problem that we are trying to solve in this issue.

After creating a per diem expense in workspace chat on web, performing **Account → Troubleshoot → Clear cache and restart → Reset and refresh** and returning to the chat leaves the per diem receipt stuck in a permanent loading state: the receipt content is visible but rendered at 50% opacity with a spinner overlay that never clears. The same broken appearance can also appear on web without the reset step in some cases. The issue is staging-only (not reproducible on production) and affects web (Chrome/Safari on macOS and Windows), not native iOS/Android.

### What is the root cause of that problem?

There are two layers: a pre-existing web-only stall in the full-resolution image load, and a staging regression from #97313 that turns that silent stall into a visible, permanent loading UI.

**1. Render path for a per diem expense receipt**

Per diem transactions are returned from the server with a real `receipt.source`, so they are **not** treated as eReceipts. `ReportActionItemImage` resolves both a full-res thumbnail (`.1024.jpg`) and a low-res preview (`.320.jpg`), then passes `previewUri` into `ReceiptImage` → `ThumbnailImage` → `ImageWithSizeCalculation` → `ImageWithLoading`:

**2. Underlying stall (pre-existing on production, invisible there)**

On web, auth-required images go through `useCachedImageSource`, which returns `null` to `expo-image` while its `fetch` is in flight. `BaseImage` manually calls `onLoadStart` whenever the source changes, which sets `ImageWithLoading.isLoading = true`. If the full-res `.1024.jpg` never settles (no `onLoad` and no `onError`), `isLoading` stays latched `true` indefinitely.

Reset and refresh makes this much more likely because it wipes both the `AUTH_IMAGES` Cache API store and the service-worker `user-media` cache, forcing every receipt derivative back onto the network:

Three specific regressions from #97313 combine to produce the "infinite loading" appearance:

| Before #97313 (production) | After #97313 (staging) |
|---|---|
| Preview renders at **full opacity** once loaded | Preview always rendered at **50% opacity** (`opacitySemiTransparent`) while `isLoading` |
| `isThumbnailLoading` flipped to `false` on preview `onLoad`, hiding the spinner | `isThumbnailLoading` removed entirely |
| Spinner gated by `!previewUri \|\| isThumbnailLoading` **and** `!isImageCached` (200ms anti-flash) | Spinner shown whenever `previewUri && isLoading`, skipping the anti-flash gate |

When the full-res load stalls, `isLoading` stays `true` forever. Before #97313 that looked like a slightly soft receipt at full opacity with no spinner. After #97313 it looks like a permanently dimmed receipt with a permanent spinner — exactly what the testers reported.

**Regression context:** #97313 also caused #98559 and #98561; #98568 reverted the deferred-loading half of that PR but left these `ImageWithLoading` changes in place, which is why the bug persisted through `9.4.53-7`.

**LAST thing that works correctly:** the `.320.jpg` preview fetch succeeds and paints the receipt content.

**FIRST thing that goes wrong:** `ImageWithLoading` never clears its visible loading state because it now ties spinner visibility and preview opacity to the full-res `.1024.jpg` load completing, which may never emit `onLoad`/`onError` on web.

### What changes do you think we should make in order to solve the problem?

Restore the pre-#97313 loading-state behavior in `src/components/ImageWithLoading.tsx` only. This is a single-file, ~10-line roll-forward that matches the production pattern already proven safe. Make these four focused changes:

**1. Re-add `isThumbnailLoading` state** (after `isLoading`):

+ `const [isThumbnailLoading, setIsThumbnailLoading] = useState(!!previewUri);`

**2. Remove dimming from the preview placeholder** (line ~100):

- `style={[styles.w100, styles.h100, styles.opacitySemiTransparent, style]}`
+ `style={[styles.w100, styles.h100, style]}`

**3. Clear thumbnail loading once the preview paints** (line ~102):

- `onLoad={onLoad}`
+ `onLoad={(e) => { setIsThumbnailLoading(false); onLoad?.(e); }}`

**4. Restore the production spinner gate and session-reset handling** (lines ~128 and ~133):

+ `setIsThumbnailLoading(!!previewUri);` inside `waitForSession`
- `{(previewUri ? isLoading : isLoading && !isImageCached) && !isOffline && (`
+ `{isLoading && (!previewUri || isThumbnailLoading) && !isImageCached && !isOffline && (`

**Why this is the best fix:**

1. **Fixes the deploy blocker, not just the per-diem path.** Any auth-required receipt image that passes a `previewUri` (report previews, thumbnails, hover-zoom receipts) hits `ImageWithLoading`. Restoring `isThumbnailLoading` fixes all of them with one change.
2. **Root cause vs symptom.** The underlying full-res stall in `useCachedImageSource`/`BaseImage` is real but pre-existing and invisible on production; fixing it here would be a larger, riskier change. Decoupling visible loading state from full-res settlement is the correct contract: once the preview is readable, the user should not see a spinner.
3. **Minimal blast radius.** One file, no changes to #97313's `previewUri`/`thumbnail320` plumbing or hover-zoom behavior. Full-res images still load in the background when they can; users just stop seeing a permanent spinner when they cannot.
4. **Follows an existing pattern.** This is byte-identical to production behavior before `88429801b05`; no new abstraction needed.
5. **Covers all reproduction paths.** Works after reset-and-refresh (cold cache), without reset (mkhutornyi's alternate repro), and for any receipt type using `previewUri` — not only per diem.

The underlying `useCachedImageSource` hang (where full-res images can stall with no `onLoad`/`onError` on web) should be tracked as a separate, non-blocking follow-up.

### What alternative solutions did you explore? (Optional)

1. **Full revert of #97313** — Not viable. #98568 already reverted the deferred-loading half, and `ReceiptImage` still depends on the remaining plumbing. A targeted `ImageWithLoading` fix is smaller and safer.
2. **Fix `useCachedImageSource` / `BaseImage` to always emit `onError` when fetch stalls** — Addresses the deeper stall but is a broader change with higher blast radius across all auth-required images; better suited to a dedicated follow-up issue rather than a deploy-blocker hotfix.
3. **Keep #97313's dimmed preview + always-on spinner and add a timeout to force-clear `isLoading`** — Adds timing assumptions and could hide legitimate slow loads; restoring `isThumbnailLoading` is simpler and matches production semantics.
4. **Per-diem-specific handling in `ReportActionItemImage` or `ReceiptImage`** — Would miss the same stall on every other receipt type that uses `previewUri`, and duplicates logic that already belongs in `ImageWithLoading`.
