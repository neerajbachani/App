## Proposal

### Please re-state the problem that we are trying to solve in this issue.

When a member submits a report and the approver's vacation delegate is not a member of the workspace policy, a system-generated notice ("This report was sent to X instead of their Vacation Delegate Y because they are not a member of this report's policy") appears in the report timeline attributed to the submitter — with their avatar, bold text, and a layout that reads like a user-authored message rather than a muted system notification.

### What is the root cause of that problem?

Submission with a vacation-delegate routing failure produces an `ACTION_DELEGATE_SUBMIT` (`DELEGATESUBMIT`) report action (see `CONST.REPORT.ACTIONS.TYPE.ACTION_DELEGATE_SUBMIT`) alongside the normal `SUBMITTED` action. The vacation-delegate notice is a structural system message, but two App-side gaps cause the broken presentation:

**1. Actor attribution uses the submitter instead of Concierge**

`ReportActionItemSingle` always renders an avatar/header row via `useReportActionAvatars` → `getReportActionActorAccountID`. For `DELEGATESUBMIT`, there is no dedicated case, so the switch falls through to `default` and returns `reportAction?.actorAccountID` — the submitter:

**Why this explains the reported symptoms and platforms**

- Reproduces on web (Chrome/Safari) because rendering is entirely App-side; no native-specific code path.
- Bold text + cracked layout: chat-renderer fallthrough (gap #2) or `SUBMITTEDCLOSED` gap (#3).
- Submitter avatar + "authored by user" appearance: `DELEGATESUBMIT` uses submitter's `actorAccountID` (gap #1). The adjacent grouped `SUBMITTED` action then shows the muted "submitted" label below, which matches the screenshots.
- Does not reproduce for normal `SUBMITTED` actions without a vacation-delegate routing failure, because those go through `ApprovalFlowContent` and never hit the chat renderer.

### What changes do you think we should make in order to solve the problem?

Apply three small, frontend-only changes that together cover all reproduction paths:

**1. Route `DELEGATESUBMIT` actions through Concierge for avatar/name attribution**

In `getReportActionActorAccountID`, add a case before `default` (matching the existing harvesting / DEW / automatic-action Concierge overrides):

```diff
+        case CONST.REPORT.ACTIONS.TYPE.ACTION_DELEGATE_SUBMIT:
+            return CONST.ACCOUNT_ID.CONCIERGE;
+
         default:
             return reportAction?.actorAccountID;
```

`DELEGATESUBMIT` is always a system-generated routing notice (`getDelegateSubmitMessage` builds the copy from `originalMessage.isOnPolicy`, `originalManager`, and `delegate`). Concierge attribution is consistent with how other automated routing messages are displayed and directly addresses the avatar issue in #98045.

**2. Never fall through to `ChatMessageContent` for `DELEGATESUBMIT`**

Remove the `if (delegateSubmitMessage)` guard so the muted system-message renderer always handles this action type:

When `originalManager`/`delegate` are missing, `getDelegateSubmitMessage` already logs a warning and returns `''`, which safely renders as an empty muted block rather than falling through to the bold chat renderer. No backend flag is needed — `isOnPolicy` already exists on `OriginalMessageDelegateSubmit`.

**Blast radius:** Changes are scoped to vacation-delegate routing notices and submit/approve system-message styling. Normal user comments, successful vacation-delegate submissions (which use `SUBMITTED` + `VacationDelegateText`), and harvesting/DEW flows are unaffected.

### What alternative solutions did you explore? (Optional)

- **MelvinBot's proposal (add `SUBMITTED_AND_CLOSED` to `isApprovedOrSubmittedReportAction` only):** Correct for the legacy `SUBMITTEDCLOSED` path and duplicate #96454, but does not fix the primary `DELEGATESUBMIT` path where #98045's avatar attribution bug originates. Incomplete on its own.

- **j3ffffff's proposal (backend `delegateNotInPolicy` flag + Concierge override):** The Concierge direction is right, but a new backend field is unnecessary — `DELEGATESUBMIT` already carries `isOnPolicy` in `originalMessage`, and the action type itself identifies the system message. Guarding `VacationDelegateText` with a new flag is also unnecessary for this repro because the failure notice lives on the separate `DELEGATESUBMIT` action, not in `VacationDelegateText`'s "to X as vacation delegate for Y" copy.

- **String-matching `action.message` for "not a member":** Rejected — fragile across locales and duplicates logic already centralized in `getDelegateSubmitMessage`.

- **Dedicated new system-message renderer:** Rejected — the existing muted `RenderHTML` + Concierge avatar pattern used by `TAKE_CONTROL`, `REROUTE`, and DEW failure actions already produces the desired output; the action type was just missing from the actor override and had a fallthrough guard.

### What specific scenarios should we cover in automated tests?

- `DELEGATESUBMIT` with `isOnPolicy: false` renders with Concierge avatar (not submitter) and muted vacation-delegate failure text.
- `DELEGATESUBMIT` with missing `originalManager`/`delegate` does not fall through to `ChatMessageContent` (no bold `ReportActionItemMessageHeaderSender` styling).
- `SUBMITTED_AND_CLOSED` action whose `action.message` contains vacation-delegate TEXT fragments renders muted and on a single line (regression for #96454).
- Existing `SUBMITTED` + successful vacation delegate flow still shows the submitter avatar with `VacationDelegateText` unchanged.
