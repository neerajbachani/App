## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On a **Submit** workspace (`policy.type === 'submit2026'`) with the `submit2026` beta, enabling **Workspace settings → Reports → Report fields** correctly routes through the upgrade flow. After clicking **Upgrade** and **Got it, thanks**, the workspace is upgraded and Report fields turns on. If the user then disables Report fields and re-enables it, the **Upgrade** page opens again instead of toggling the feature on directly. The same re-prompt pattern exists for the sibling **Prevent members from changing custom names** toggle on the same page.

### What is the root cause of that problem?

This is a **plan-tier mismatch** between (1) what the Reports toggles treat as "upgrade complete" and (2) what the Submit upgrade path actually writes to `policy.type`.

**1. Reports toggles only skip the upgrade redirect for Control workspaces**

**3. The resulting loop**

| Step | `policy.type` | Reports toggle sees | Result |
|------|---------------|---------------------|--------|
| First enable (Submit WS) | `submit2026` | `!isControlPolicy` → true | Upgrade page (correct) |
| After Upgrade → Got it, thanks | `team` (Collect) | Report fields enabled via `confirmUpgrade` | Feature ON |
| Disable Report fields | `team` | — | Feature OFF |
| Re-enable | `team` | `!isControlPolicy` still true | **Upgrade page again (bug)** |

After the first upgrade the workspace is **Collect** (`team`), not **Control** (`corporate`). The legacy `!isControlPolicy` gate never clears, so every re-enable re-opens Upgrade.

**4. Why this is Submit-only and hard to repro without the right preconditions**

- The `?? TEAM` fallback only runs inside the Submit branch (`isUpgradingFromSubmitPolicy`) shown above. Native **Collect** workspaces take `upgradeToCorporate()`, which lands on Control — so the re-enable loop does not occur there.
- Reproduction requires **both** a Submit workspace (`policy.type === 'submit2026'`) **and** the `submit2026` beta. Without both, the client takes a different upgrade path and the bug cannot appear — which explains inconsistent QA retests.
- The upgrade page copy explicitly tells the user Report fields require **Control**, but the confirmation after upgrade can say **Collect** — exposing the mismatch:

### What changes do you think we should make in order to solve the problem?

Add the missing `requiredPlan` to the `reportFields` upgrade mapping so the Submit upgrade target matches the existing Reports-page gate and upgrade-page copy. This is the same single-source-of-truth fix #92872 established for other Control-gated features.

In `src/CONST/index.ts`, add one line to the existing `reportFields` entry:

                 icon: 'Pencil',
+                requiredPlan: this.POLICY.TYPE.CORPORATE,

With `requiredPlan` present, `targetType` at `WorkspaceUpgradePage.tsx:193` resolves to `CORPORATE`, `upgradeSubmit` promotes the workspace to Control, `isControlPolicy(policy)` becomes `true`, and re-enabling Report fields calls `enablePolicyReportFields` directly instead of reopening Upgrade.

**Why this is the best fix**

- Fixes the **root cause** (upgrade lands below the gate) rather than weakening the gate.
- **One property, one file** — smallest diff, follows the established #92872 contract.
- Preserves existing behavior for Collect workspaces (still route to Control upgrade via `!isControlPolicy`).
- Aligns upgrade target with user-facing copy ("Control plan") and the Reports toggle gate.
- `reportFields.id` is not in `SUBMIT_FEATURE_IDS`, so after upgrade `confirmUpgrade` still calls `enablePolicyReportFields(policyID, true)` via the default branch — first-enable behavior is unchanged.

**Blast radius / edge cases checked**

- Submit first-enable: still shows Upgrade, now correctly upgrades to Control.
- Collect workspace (never Submit): unchanged — uses `upgradeToCorporate()`.
- HR / rules / perDiem: unchanged — already declare `requiredPlan: CORPORATE`.
- **`policyPreventMemberChangingTitle`**: shares the same `!isControlPolicy` gate on Reports but is deliberately excluded from the feature lookup in `WorkspaceUpgradePage` (line 115), so adding `requiredPlan` there would not fix its upgrade target; that toggle needs a separate follow-up.

### What alternative solutions did you explore? (Optional)

**1. Replace `!isControlPolicy` with `tryNavigateToSubmitWorkspaceUpgrade` on Reports (Melvin / aswin-s proposals)**

`tryNavigateToSubmitWorkspaceUpgrade` only redirects while `isSubmitPolicy(policy)` is still true:

App/src/libs/PolicyUtils.ts
Lines 1437 to 1445 in 380ee969b9f
```typescript
function tryNavigateToSubmitWorkspaceUpgrade(policy: OnyxEntry<Policy>, isEnabling: boolean, upgradeFeatureAlias: string, backTo?: string): boolean {
    if (!policy?.id || !isEnabling || !isSubmitPolicy(policy)) {
        return false;
    }
    Navigation.navigate(ROUTES.WORKSPACE_UPGRADE.getRoute(policy?.id, upgradeFeatureAlias, backTo ?? ROUTES.WORKSPACE_MORE_FEATURES.getRoute(policy?.id)));
    return true;
}
```
https://github.com/Expensify/App/blob/380ee969b9f819845c2ffe2a92cd5c92d63e28e6/src/libs/PolicyUtils.ts#L1437-L1445

This stops the re-enable loop after Submit→Collect upgrade, but it also **drops the Collect→Control upgrade redirect** for any workspace that is no longer Submit — including native Collect workspaces. That contradicts the Control-only gate and upgrade copy. Rejected.

**2. `tryNavigateToSubmitWorkspaceUpgrade` + legacy Control redirect when beta is off (dilshodmackbook-sketch / neerajbachani proposals)**

Preserves Collect→Control for accounts without the beta, but under the beta a Collect workspace can enable Report fields without ever upgrading to Control. That weakens the feature gate instead of aligning the upgrade target. Rejected for the same product-tier reason.

**3. Hardcoded Control-feature ID set in `WorkspaceUpgradePage` (emkhalid proposal)**

Would work mechanically but reintroduces the "forgot to add the new feature" failure mode that #92872 removed in favor of declarative `requiredPlan`. Rejected.

**4. Persist `type: CORPORATE` in `upgradeToCorporate` success data (KJ21-ENG proposal)**

Incorrect root cause — Submit workspaces use `upgradeSubmit`, not `upgradeToCorporate`, and the optimistic `policy.type` update from `upgradeSubmit` already writes the `targetType`. The bug is the wrong `targetType`, not a missing persist.

### What specific scenarios should we cover in automated tests?

- Opening the Report fields upgrade page for a Submit workspace and clicking Upgrade calls `UpgradeSubmit` with `targetType: CORPORATE` (mirror the existing `preventSelfApproval` test in `tests/ui/WorkspaceUpgradeTest.tsx`).
- After a Submit workspace is upgraded to Control via Report fields, re-enabling Report fields on `WorkspaceReportsPage` does not navigate to `WORKSPACE_UPGRADE` (integration or manual regression).
