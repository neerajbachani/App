## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On web, when the Manual tab is selected on the expense-creation RHP (`IOURequestStartPage`), keyboard users cannot Tab to the header Back button after opening **Create expense** from the composer (or the equivalent Split expense Manual tab). Scan/Distance tabs do not exhibit this problem, and the bug is limited to desktop web (Chrome/Safari) where `FocusTrapForScreen` runs.

### What is the root cause of that problem?

The header Back button **is** correctly included in the parent screen's focus trap — this is not a missing-`tabIndex` issue. `IOURequestStartPage` registers three trap containers (header, tab bar, active tab) and passes them to its `ScreenWrapper`:

Because the embedded confirmation's trap has no custom `containerElements`, it defaults to its own wrapper node only. That inner trap sits on top of `sharedTrapStack` and confines Tab to the confirmation form. The parent header container (where the Back button lives) is outside the inner trap, so Tab never reaches it. Scan/Distance tabs avoid this because their embedded step components either skip `ScreenWrapper` entirely (`shouldShowWrapper={false}`) or never nest a second active trap.

This regression class was introduced when the confirmation screen was embedded on the start page (hiding the duplicate header in commit `302b6654834`) without also disabling the child screen's focus trap — the same mistake `NewChatSelectorPage` already solved for its tab children.

### What changes do you think we should make in order to solve the problem?

Disable the embedded confirmation screen's focus trap so the parent `IOURequestStartPage` trap (which already includes the header, tab bar, and active tab containers) remains authoritative. This matches the established pattern used by tab content embedded inside `NewChatSelectorPage`:

Apply the same fix in `IOURequestStepConfirmation`:

```tsx
<ScreenWrapper
    shouldEnableMaxHeight={canUseTouchScreen() && !isMobileSafari()}
    shouldAvoidScrollOnVirtualViewport={!isMobileSafari()}
    testID="IOURequestStepConfirmation"
    // Disable the focus trap when embedded on IOURequestStartPage so the parent trap (which includes the header Back button) stays active.
    focusTrapSettings={shouldHideHeader ? {active: false} : undefined}
>
```

**Why this is the best fix:** It addresses the root cause (nested active trap on `sharedTrapStack`) in one line, follows an existing in-repo pattern, leaves the standalone confirmation route (`shouldHideHeader={false}`) unchanged, and covers every Manual-tab reproduction path (Create expense, Split expense, and any `IOURequestStartPage` embed) without touching shared trap wiring or header markup.

**Blast radius:** Only affects web keyboard navigation for the embedded-manual-tab case. Standalone `IOURequestStepConfirmation` navigation, Scan/Distance/Per diem tabs, and native platforms are unchanged.

### What alternative solutions did you explore? (Optional)

- **Wire the parent header into the inner trap's `containerElements`.** Rejected — it duplicates trap ownership, fights `IOURequestStartPage`'s existing three-container setup, and is harder to keep in sync when tabs switch.
- **Remove the inner `ScreenWrapper` entirely when embedded.** Rejected — `ScreenWrapper` still provides keyboard-avoidance, offline indicators, and layout behavior the confirmation screen relies on; disabling only the trap is the minimal change.
- **Adjust Manual-tab auto-focus / `focus-trap` fallback behavior (amount-input theory).** Rejected for this issue — that path applies to the legacy amount step (`IOURequestStepAmount` with `shouldShowWrapper={false}`), not to the embedded confirmation flow that reproduces here. The header is already in the parent trap; the inner trap is what blocks Tab from reaching it.

### What specific scenarios should we cover in automated tests?

- Assert that when `IOURequestStepConfirmation` is rendered with `shouldHideHeader`, its `ScreenWrapper` receives `focusTrapSettings={{active: false}}`.
- Assert that when `shouldHideHeader` is false/omitted (standalone confirmation route), the focus trap remains active (no regression).
- (Optional browser/integration) On `IOURequestStartPage` Manual tab with `newManualExpenseFlow` beta enabled, Tab from a confirmation-form control eventually focuses the header Back button.
