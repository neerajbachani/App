## Proposal

### Please re-state the problem that we are trying to solve in this issue.

When a user uploads multiple receipts together on the expense confirmation screen and submits them in one batch, a configured expense agent should run against every newly created expense. Instead, only one expense is processed by the agent; the remaining expense(s) in the batch are never evaluated by the automation rules.

### What is the root cause of that problem?

The App client correctly submits one backend write command per expense in the batch. The bug is that those commands intentionally share report-level optimistic IDs, and the expense-agent trigger on the backend appears to dedupe on those shared report-level events instead of firing once per transaction.

**Mechanism:** Uploading expenses one-at-a-time runs `requestMoney()` / `trackExpense()` separately, so each upload produces its own report-level lifecycle and the agent fires once per upload. Uploading multiple receipts in a single confirmation batch produces N backend writes but only **one** report-preview / report-created lifecycle, so an agent trigger keyed on those shared report-level action IDs runs exactly once — matching the reported symptom. This is a backend trigger/dedup issue (consistent with the `Internal` label), not a missing client write.

### What changes do you think we should make in order to solve the problem?

**Fix belongs in the Concierge / expense-agent backend trigger (not `Expensify/App`).** The client is behaving correctly by attaching multiple expenses to one report with one preview action.

Update the expense-agent trigger so it fires **once per transaction** (or once per IOU/TRACK report action), keyed by `transactionID` or `reportActionID`, instead of deduping on shared report-level IDs like `reportPreviewReportActionID`, `createdIOUReportActionID`, or `createdChatReportActionID`.

Pseudo-change in the backend agent-trigger handler:

```php
// Before (buggy): dedupes on report-level action → only first expense in a batch runs
if (alreadyProcessed($reportPreviewReportActionID)) {
    return;
}
triggerAgent($reportPreviewReportActionID);

// After (correct): dedup on the per-expense identifier present in every write
if (alreadyProcessed($transactionID)) {
    return;
}
triggerAgent($transactionID, $reportActionID);
```

**Why this is the best fix:**
- Fixes all batch-upload reproduction paths (`REQUEST_MONEY`, `TRACK_EXPENSE`, and workspace tracked-expense variants) without changing App optimistic report structure.
- Preserves the existing UX of one report preview for multiple expenses on the same report.
- Aligns agent behavior with user expectation: N uploaded expenses ⇒ N agent evaluations.
- Matches how other batch flows already rely on per-transaction uniqueness — e.g. bulk duplicate generates a fresh `optimisticCreatedReportActionID` per expense while intentionally sharing the preview ID across items on the same report (`Duplicate.ts` lines 843–845, 1299).

**Verification (backend, with log access):**
1. Reproduce with two simultaneous receipt uploads.
2. Confirm two distinct `REQUEST_MONEY`/`TRACK_EXPENSE` commands arrive with two different `transactionID`s and two different `reportActionID`s but the same `reportPreviewReportActionID`.
3. Confirm the agent trigger currently fires once on the shared preview/created action and does not re-fire on the second IOU action.
4. After the fix, confirm two agent runs (one per `transactionID`).

**Blast radius:** No App changes required. Existing single-expense uploads, sequential uploads, and report preview rendering remain unchanged because report-level IDs stay shared by design.

### What alternative solutions did you explore? (Optional)

1. **Generate unique `optimisticReportPreviewActionID` per loop iteration in `useExpenseSubmission.ts`** — Rejected. Subsequent iterations explicitly reuse/update the existing preview via `getReportPreviewReportAction()`, so all writes would still share one preview action ID. Creating multiple preview actions per report would break the established one-preview-per-report model.

2. **Split batch uploads into separate confirmation submissions from the client** — Rejected. This would be a fragile workaround, degrade UX, and still wouldn't fix other server-side batch creation paths (e.g. bulk duplicate) that legitimately share preview IDs.

3. **Add `shouldDeferAutoSubmit` to multi-receipt confirmation (mirroring bulk duplicate)** — Rejected for this bug. That flag only defers report auto-submit during batch creation; it does not cause the agent to skip individual transactions, and `useExpenseSubmission` doesn't pass it today.

4. **Client-side agent invocation** — Rejected. AgentZero / workspace agent rules are enforced server-side; there is no App action that can invoke the expense agent per transaction today.
