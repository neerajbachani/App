## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On native iOS/Android, when a user opens Concierge Anywhere from the report sidebar button while viewing an expense report with transactions, and asks Concierge to update categories (e.g. "Update all transactions in this report to have category Car"), Concierge replies that the chat/report has no expenses. The same flow works on web because the side panel keeps the source report visible and its context is attached to the outgoing message.

### What is the root cause of that problem?

Concierge Anywhere on native navigates away from the expense report into the Concierge chat, but the App never attaches the source report as `sidePanelContext` on the `AddComment` API call. The backend therefore only sees the empty Concierge chat and correctly responds that there is nothing to update.

The failure happens at three linked points in the native path:

### What changes do you think we should make in order to solve the problem?

Thread the source expense report onto the Concierge navigation entry as an optional route param (`sourceReportID`), scoped to that screen instance. This mirrors how web keeps context per side-panel session, survives multiple Concierge stack entries, and requires no global Onyx key.

**1. Add `sourceReportID` to the report route (only set from the native sidebar button).**

`ROUTES.REPORT_WITH_ID.getRoute` — add optional 6th param and append it as a query param:

```diff
-        getRoute: (reportID: string | undefined, reportActionID?: string, referrer?: string, backTo?: string, secureKey?: string) => {
+        getRoute: (reportID: string | undefined, reportActionID?: string, referrer?: string, backTo?: string, secureKey?: string, sourceReportID?: string) => {
             ...
+            if (sourceReportID) {
+                queryParams.push(`sourceReportID=${encodeURIComponent(sourceReportID)}`);
+            }
```

Declare it on screen params in `types.ts` and add parse/stringify in `linkingConfig/config.ts` (required because `navigateToConciergeChat` navigates by URL string).

**2. Capture and pass the source report only from `SidePanelButton/index.native.tsx`.**

This is the only entry that should attach context. The search "Ask Concierge" path goes through `useOpenConciergeAnywhere` → `openConciergeAnywhere` and must not carry a source report:

```diff

+                        false,
+                        undefined,
+                        undefined,
+                        undefined,
+                        undefined,
+                        sourceReportID && sourceReportID !== conciergeReportID ? sourceReportID : undefined,
+                    );
                 }}
```

**3. Thread `sourceReportID` through `navigateToConciergeChat`.**

Each pushed Concierge screen retains its own `sourceReportID` in `route.params`, so navigating back to an earlier Concierge entry restores the correct report (A vs B). Search/LHN/deep-link entries call `navigateToConciergeChat` without `sourceReportID`, so they behave as today. Web is unchanged — it still builds context from live side-panel state.

**Blast radius:** six files touched (`ROUTES.ts`, `types.ts`, `linkingConfig/config.ts`, `Report/index.ts`, `SidePanelButton/index.native.tsx`, `useSidePanelContext.ts`). No backend change expected — the backend already consumes `sidePanelContext.reportID` for web. Scope is `{reportID}` only, which covers the reported repro ("update all transactions in this report"); multi-select transaction context would need additional work.

### What alternative solutions did you explore? (Optional)

- **Reuse `currentReportID` in `useSidePanelContext`:** Rejected. On native, navigation to Concierge updates the topmost report to the Concierge chat before the composer runs, so `currentReportID` would always resolve to the empty Concierge report.

- **Global Onyx key (`CONCIERGE_SOURCE_CONTEXT`):** Rejected. A single global value collides when multiple Concierge screens exist on the stack (sidebar open from report A, navigate to B, sidebar open again — back-nav to the first Concierge would read the wrong report). Route params are inherently scoped per navigation entry.

- **Capture in `useOpenConciergeAnywhere/index.native.tsx`:** Rejected. The sidebar button does not call `openConciergeAnywhere`; it calls `navigateToConciergeChat` directly. Capturing in `openConciergeAnywhere` would incorrectly attach context to the search "Ask Concierge" path (`useAskConcierge.tsx`).

- **Native side-panel overlay matching web:** Rejected as a product/design change with much larger scope than the targeted fix.

### What specific scenarios should we cover in automated tests?

- Assert that when Concierge is opened via the native sidebar button from an expense report, the `AddComment` request includes `sidePanelContext` with the source report's `reportID`.
- Assert that opening Concierge via search "Ask Concierge" does not include `sourceReportID` in route params or `sidePanelContext` in the API call.
- Assert that two Concierge entries pushed from different reports each retain their own `sourceReportID` after back navigation (stack `[ReportA, Concierge#1, ReportB, Concierge#2]` → Concierge#1 still references A).
