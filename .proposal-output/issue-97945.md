## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On native iOS/Android, when a user opens Concierge Anywhere from the report sidebar button while viewing an expense report with transactions, and asks Concierge to bulk-update categories (e.g. "Update all transactions in this report to have category Car"), Concierge replies that the chat/report has no expenses. The same flow works on web because the side panel keeps the source report visible and attaches its context to the outgoing message.

### What is the root cause of that problem?

On native, Concierge Anywhere navigates away from the expense report into the Concierge chat, but the App never attaches the source report as `sidePanelContext` on the `AddComment` API call. The backend therefore only sees the empty Concierge chat and correctly responds that there is nothing to update.

The failure is a **missing context handoff** at three linked points:

**1. `useSidePanelContext` only builds context when `isInSidePanel` is true (web-only).**

### What changes do you think we should make in order to solve the problem?

Thread the source expense report onto the Concierge navigation entry as an optional route param (`sourceReportID`), scoped to that screen instance. This follows the existing pattern of report route query params like `referrer` and `secureKey`, survives multiple Concierge stack entries, and requires no global Onyx key.

**1. Add `sourceReportID` to `ROUTES.REPORT_WITH_ID.getRoute`:**

```diff
-        getRoute: (reportID: string | undefined, reportActionID?: string, referrer?: string, backTo?: string, secureKey?: string) => {
+        getRoute: (reportID: string | undefined, reportActionID?: string, referrer?: string, backTo?: string, secureKey?: string, sourceReportID?: string) => {
             ...
+            if (sourceReportID) {
+                queryParams.push(`sourceReportID=${encodeURIComponent(sourceReportID)}`);
+            }
```

Declare `sourceReportID?: string` on `[SCREENS.REPORT]` in `types.ts`, and add parse/stringify in `linkingConfig/config.ts` (required because `navigateToConciergeChat` navigates by URL string).

**2. Capture and pass the source report only from `SidePanelButton/index.native.tsx`:**

```diff
+import Navigation from '@libs/Navigation/Navigation';

                 onPress={() => {
+                    const sourceReportID = Navigation.getTopmostReportId();
+                    navigateToConciergeChat(
+                        conciergeReportID,
+                        introSelected,
+                        currentUserAccountID,
+                        isSelfTourViewed,
+                        betas,
+                        false,
+                        undefined,
+                        undefined,
+                        undefined,
+                        undefined,
+                        sourceReportID && sourceReportID !== conciergeReportID ? sourceReportID : undefined,
+                    );
                 }}
```

**3. Thread `sourceReportID` through `navigateToConciergeChat`:**

Add an optional trailing `sourceReportID?: string` parameter and pass it to `getRoute`:

```diff
 function navigateToConciergeChat(
     ...
+    sourceReportID?: string,
 ) {
     ...
-        Navigation.navigate(ROUTES.REPORT_WITH_ID.getRoute(conciergeReportID), linkToOptions);
+        Navigation.navigate(ROUTES.REPORT_WITH_ID.getRoute(conciergeReportID, undefined, undefined, undefined, undefined, sourceReportID), linkToOptions);
```

**4. Build `sidePanelContext` from the route param on native in `useSidePanelContext`:**

```diff
+import {useRoute} from '@react-navigation/native';

     const route = useRoute<PlatformStackRouteProp<ReportsSplitNavigatorParamList, typeof SCREENS.REPORT>>();
+    const sourceReportID = route.params?.sourceReportID;

     return useMemo(() => {
-        if (conciergeReportID !== reportID || !isInSidePanel) {
+        if (conciergeReportID !== reportID) {
             return undefined;
         }

+        if (!isInSidePanel) {
+            return sourceReportID ? {reportID: sourceReportID} : undefined;
+        }
         ...
-    }, [conciergeReportID, reportID, isInSidePanel, ...]);
+    }, [conciergeReportID, reportID, isInSidePanel, sourceReportID, ...]);
```

**5. Relax the send guard so native context is included:**

```diff
-    if (isInSidePanel && isConciergeChat && sidePanelContext && commandName === WRITE_COMMANDS.ADD_COMMENT) {
+    if (isConciergeChat && sidePanelContext && commandName === WRITE_COMMANDS.ADD_COMMENT) {
         parameters.sidePanelContext = JSON.stringify(sidePanelContext);
     }
```

Each pushed Concierge screen retains its own `sourceReportID` in `route.params`, so back-nav restores the correct report (Concierge#1 → A, Concierge#2 → B). Search/LHN/deep-link entries call `navigateToConciergeChat` without `sourceReportID`, so they behave as today. Web is unchanged.

**Blast radius:** six files (`ROUTES.ts`, `types.ts`, `linkingConfig/config.ts`, `Report/index.ts`, `SidePanelButton/index.native.tsx`, `useSidePanelContext.ts`). No backend change expected — the backend already consumes `sidePanelContext.reportID` for web. Scope is `{reportID}` only, covering the reported repro; multi-select transaction context would need additional work.

### What alternative solutions did you explore? (Optional)

- **Reuse `currentReportID`:** Rejected. Navigation to Concierge updates the topmost report before the composer runs, so it always resolves to the empty Concierge chat.

- **Global Onyx key (`CONCIERGE_SOURCE_CONTEXT`):** Rejected. Collides when multiple Concierge screens exist on the stack; route params are inherently scoped per navigation entry.

- **Capture in `useOpenConciergeAnywhere/index.native.tsx`:** Rejected. The sidebar button never calls this hook; capturing here would incorrectly attach context to the search "Ask Concierge" path.

- **Native side-panel overlay matching web:** Rejected as a product/design change with much larger scope.

### What specific scenarios should we cover in automated tests?

- Assert that opening Concierge via the native sidebar button from an expense report includes `sidePanelContext` with the source report's `reportID` in the `AddComment` request.
- Assert that opening Concierge via search "Ask Concierge" does not include `sourceReportID` in route params or `sidePanelContext` in the API call.
- Assert that two Concierge entries pushed from different reports each retain their own `sourceReportID` after back navigation (stack `[ReportA, Concierge#1, ReportB, Concierge#2]` → Concierge#1 still references A).
