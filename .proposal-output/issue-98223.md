## Proposal

### Please re-state the problem that we are trying to solve in this issue.

When a workspace has commuter exclusions enabled, manual and odometer distance expenses cannot be edited through the App UI (Save is blocked with the map/GPS-required modal). However, sending a natural-language chat command such as "Edit distance to 200 miles" on the same expense still updates the distance. The command path bypasses the client-side enforcement that PR #93848 added for the UI.

### What is the root cause of that problem?

PR #93848 introduced commuter-exclusion enforcement only on App UI entry points via `useCommuterExclusionGuard`. That hook blocks manual/odometer distance flows when the workspace policy has commuter exclusions configured (`isCommuterExclusionEnabled`), showing a modal and returning early so callers never submit the edit.

The chat command "Edit distance to 200 miles" is the critical gap: it is parsed and applied **server-side** by Concierge/backend logic. A codebase search finds no App handler that parses or intercepts this command — it never mounts `IOURequestStepDistanceManual`, never calls `useCommuterExclusionGuard`, and never goes through `updateMoneyRequestDistance`. The server applies the new distance and pushes the updated transaction back to Onyx directly. That is why the bug reproduces on web (Windows Chrome in the report) and would reproduce on every platform equally — there is no App code on the command execution path to enforce the rule.

**Mechanism:** this is a missing server-side guard, not a race condition. The last correct step in the UI path is the modal from `useCommuterExclusionGuard`. The first incorrect step in the command path is the backend accepting and applying a manual-distance quantity change for a policy with commuter exclusions enabled.

### What changes do you think we should make in order to solve the problem?

The fix must enforce the same rule on the **server** so it holds regardless of whether the edit is initiated from the App UI or a chat command. App-only changes cannot block a server-initiated Onyx update.

#### 1. Backend (required — closes the reported command bypass)

In the backend handler for `UpdateMoneyRequestDistance` and in the Concierge natural-language command parser that maps "Edit distance to …" to a distance update, reject the edit when **all** of the following are true:

- The expense belongs to a policy where commuter exclusions are enabled (`policy.commuterExclusions` is set).
- The expense is a manual or odometer distance request (`iouRequestType` is `distance-manual` or `distance-odometer`).
- The request changes the reimbursable distance quantity (as opposed to a map/GPS route-only edit where exclusions can be recomputed from the route).

Return the same user-facing error copy the App already uses (`distance.error.mapOrGpsDistanceRequired.*`) so the command reply matches the UI modal. Map/GPS distance edits that only change the selected route should continue to work, consistent with existing App behavior for route-based expenses.

#### 2. App (defense-in-depth — keeps App-initiated API calls aligned)

Extract the guard condition into a shared pure helper (mirroring the existing report-move helper pattern) and call it from `updateMoneyRequestDistance` so no future App caller can skip the UI hook:

```diff
// src/libs/PolicyDistanceRatesUtils.ts
+import {isManualDistanceRequest, isOdometerDistanceRequest} from '@libs/TransactionUtils';
+import type Transaction from '@src/types/onyx/Transaction';
+import type {OnyxEntry} from 'react-native-onyx';
+
+function shouldBlockManualOrOdometerDistanceEditForCommuterExclusion(transaction: OnyxEntry<Transaction>, policy: Policy | null | undefined): boolean {
+    return isCommuterExclusionEnabled(policy) && (isManualDistanceRequest(transaction) || isOdometerDistanceRequest(transaction));
+}
```

```diff
// src/libs/actions/IOU/UpdateMoneyRequest.ts
+import {shouldBlockManualOrOdometerDistanceEditForCommuterExclusion} from '@libs/PolicyDistanceRatesUtils';
+
 function updateMoneyRequestDistance({...}) {
+    const isChangingManualOrOdometerDistance = distance !== undefined || odometerStart !== undefined || odometerEnd !== undefined;
+    if (isChangingManualOrOdometerDistance && shouldBlockManualOrOdometerDistanceEditForCommuterExclusion(transaction, policy)) {
+        return;
+    }
     ...
     API.write(WRITE_COMMANDS.UPDATE_MONEY_REQUEST_DISTANCE, params, onyxData);
```

This App change alone does **not** fix the command bypass (the server never calls this function for Concierge edits), but it centralizes the rule next to `isCommuterExclusionEnabled` and prevents future App regressions. The backend change is what actually satisfies the issue's expected result.

**Blast radius:** map/GPS distance edits, distance-rate edits, and expenses in workspaces without commuter exclusions are unchanged. Only manual/odometer quantity edits in workspaces with exclusions are blocked — matching the UI guard today.

### What alternative solutions did you explore? (Optional)

- **Allow editing historical manual/odometer expenses (draft PR #98368):** This relaxes the UI guard for existing expenses created before exclusions were enabled by adding an `isEditingExistingDistanceRequest` bypass to `useCommuterExclusionGuard`. That changes product behavior rather than closing the command bypass, and it would still leave commands able to edit distances that the UI currently blocks (the exact inconsistency reported here). It is a valid product discussion, but it does not satisfy the issue's stated expected result without also adding server-side enforcement for the cases that should remain blocked.

- **App-only guard in `updateMoneyRequestDistance` without backend work:** Rejected because Concierge commands never invoke this function; the server would still apply the edit and sync it to all clients.

- **Revert PR #93848:** Rejected — it would remove the working UI enforcement and the entire commuter-exclusion feature without addressing the server gap.

### What specific scenarios should we cover in automated tests?

- Assert `shouldBlockManualOrOdometerDistanceEditForCommuterExclusion` returns `true` for a manual distance transaction in a policy with commuter exclusions, and `false` for map/GPS distance or policies without exclusions.
- Assert `updateMoneyRequestDistance` does not call `API.write(UPDATE_MONEY_REQUEST_DISTANCE, …)` when changing manual/odometer distance on a policy with commuter exclusions.
- Assert `updateMoneyRequestDistance` still calls `API.write` for map-route distance edits (waypoint/route changes only) on the same policy.
- Backend/integration (outside this repo): assert "Edit distance to 200 miles" on a manual distance expense in a workspace with fixed-distance exclusion is rejected with the map/GPS-required error, while the same command on a map-based distance expense succeeds.
