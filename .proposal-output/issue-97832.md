## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On narrow native layouts (Android/iOS App), after creating a new agent the app correctly opens the new agent DM chat, but tapping the chat header back button lands on the LHN (report list) instead of the Agents settings list. The expected behavior is to return to Account > Agents, matching what happened before the "open agent DM immediately after creation" change and what already works on wide layouts.

### What is the root cause of that problem?

PR #95631 replaced the post-submit `Navigation.dismissModal()` call with layout-specific navigation so the new agent DM opens immediately via an optimistic reportID. On narrow layouts, `handleSubmit` now calls `revealRouteBeforeDismissingModal` with a bare `REPORT_WITH_ID` route:

 function revealRouteBeforeDismissingModal(route: Route, options?: {afterTransition?: () => void}) {
     if (!canNavigate('revealRouteBeforeDismissingModal', {route}) || !navigationRef.current) {
         Log.hmmm(`[Navigation] Unable to reveal route before dismissing modal. Can't navigate.`, {route});
         return;
     }
 
     requestAnimationFrame(() => {
         navigationRef.current?.dispatch({
             type: CONST.NAVIGATION.ACTION_TYPE.REPLACE_FULLSCREEN_UNDER_RHP,
             payload: {route},
         });
         // Nested rAF: the first frame commits the route insertion, the second
         // frame starts the dismiss. This ensures React processes the two dispatches
         // in separate renders so the dismiss animation is preserved. On narrow,
         // wait for the hidden destination transition first so the RHP slides out
         // over the final page instead of briefly revealing the previous page.
         requestAnimationFrame(() => {
             dismissModal({afterTransition: options?.afterTransition, waitForTransition: getIsNarrowLayout()});
         });
     });
 }

Before #95631, `handleSubmit` simply called `Navigation.dismissModal()`, which returned the user to the Agents list without opening the DM at all — so back-from-chat was never exercised on narrow layouts until this regression.

### What changes do you think we should make in order to solve the problem?

Pass `ROUTES.SETTINGS_AGENTS` as the `backTo` argument when building the revealed report route on narrow layouts only. This is a one-line change in the narrow branch of `handleSubmit`; wide layout stays untouched.

```diff
 if (getIsNarrowLayout()) {
     // Reveal the DM under the modal before dismissing so we navigate directly to it in one animation,
     // instead of dismissing to the agents list first and navigating to the DM afterward.
-    Navigation.revealRouteBeforeDismissingModal(ROUTES.REPORT_WITH_ID.getRoute(optimisticReportID));
+    // backTo points the DM header's back button at the agents list; without it, dismissing the whole
+    // settings modal stack leaves the list off the back stack, so back would fall through to the LHN.
+    Navigation.revealRouteBeforeDismissingModal(
+        ROUTES.REPORT_WITH_ID.getRoute(optimisticReportID, undefined, undefined, ROUTES.SETTINGS_AGENTS),
+    );
     return;
 }
```

Why this is the best fix:

- **Root cause, not symptom:** The Agents list is intentionally removed from the native back stack by design of `revealRouteBeforeDismissingModal`. Supplying an explicit `backTo` is the established way to restore a logical parent when the stack no longer contains it.
- **Minimal blast radius:** One file, narrow-layout branch only. No changes to shared navigation helpers, RHP stack behavior, or the wide-layout `AGENT_REPORT` path.
- **Covers all narrow reproduction paths:** Applies equally whether the agent is created from a blank form or a template, with or without a custom avatar upload, and with or without a `policyID` route param — all paths converge on the same `handleSubmit` narrow branch.
- **Uses existing plumbing:** `REPORT_WITH_ID.getRoute` already accepts `backTo`, `ReportHeader` already reads it and calls `Navigation.goBack(backTo)` → `goUp(backTo)`, and `ROUTES.SETTINGS_AGENTS` is the same route the Agents settings screen lives on.
- **Preserves #95631 behavior:** The optimistic DM still opens immediately in one animation; only the back-button destination is corrected.

**Regression / edge-case notes:** Wide-layout back-to-Agents behavior is unchanged. Offline agent creation is unaffected (navigation is fully optimistic). Deeplinking directly to the revealed report without going through agent creation would not carry this `backTo`, which is correct — the param is scoped to this creation flow only.

### What alternative solutions did you explore? (Optional)

1. **Revert to `Navigation.dismissModal()` only (pre-#95631 behavior):** Would restore back-to-Agents but removes the product requirement to open the new agent DM immediately after creation.
2. **Open the DM inside the settings RHP on narrow layouts (`AGENT_REPORT` like wide):** Would preserve stack-based back navigation, but changes the narrow UX to an in-modal chat instead of a fullscreen report, and touches navigator configuration beyond this bug.
3. **Change `revealRouteBeforeDismissingModal` to preserve part of the settings stack:** Much larger blast radius — the helper is shared by expense submit, share flows, workspace creation, and search navigation. A global change risks regressions in unrelated flows.
4. **Push Agents back onto the stack after dismiss:** Would require new navigation actions and timing coordination; more complex than the existing `backTo` param pattern with no additional infrastructure.

### What specific scenarios should we cover in automated tests?

- On narrow layout, submitting the add-agent form calls `revealRouteBeforeDismissingModal` with `REPORT_WITH_ID.getRoute(optimisticReportID, undefined, undefined, ROUTES.SETTINGS_AGENTS)`.
- On narrow layout with a `policyID` route param, the same `backTo` value is still passed (policyID affects `createAgent`, not the back destination).
- On wide layout, submit still navigates to `AGENT_REPORT` with `forceReplace: true` and does **not** call `revealRouteBeforeDismissingModal`.
