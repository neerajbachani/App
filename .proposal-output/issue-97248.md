## Proposal

### Please re-state the problem that we are trying to solve in this issue.

On native Android and iOS, when the device font size is set to maximum, the right-hand "Spend" context tag on Search Router "Go to …" navigation rows (for example "Go to Expenses", "Go to Drafts") renders with a fixed 12×12 icon that does not grow with accessibility font settings, and the descender of the letter "p" in "Spend" is clipped. This regression was introduced with the new Spend navigation suggestions added in PR #96443 and only affects the native apps — not mWeb.

 /**
  * Calculate the fontSize, lineHeight and padding when the device font size is changed, In most cases users do not change their device font size so PixelRatio.getFontScale() = 1 and this
  * method always returns the defaultValue (first param). When the device font size increases/decreases, the PixelRatio.getFontScale() value increases/decreases as well.
  * This means that if you have text and its 'fontSize' is 19, the device font size changed to the 5th level on the iOS slider and the actual fontSize is 19 * PixelRatio.getFontScale()
  * = 19 * 1.11 = 21.09. Since we are disallowing font scaling we need to calculate it manually. We calculate it with: PixelRatio.getFontScale() * defaultValue > maxValue ? maxValue :
  * defaultValue * PixelRatio.getFontScale() This means that the fontSize is increased/decreased when the device font size changes up to maxValue (second param)
  */
 function getValueUsingPixelRatio(defaultValue: number, maxValue: number): number {
     return PixelRatio.getFontScale() * defaultValue > maxValue ? maxValue : defaultValue * PixelRatio.getFontScale();
 }
https://github.com/Expensify/App/blob/380ee969b9f819845c2ffe2a92cd5c92d63e28e6/src/styles/variables.ts#L3-L12

At maximum font scale this produces a **font size / line height mismatch**: `fontSizeLabel` caps at 19px while `lineHeightSmall` caps at only 16px, so the single-line `TextWithTooltip` (`numberOfLines={1}`) clips the descender of "p". The icon symptom comes from the same component hard-coding a 12×12 icon size instead of using a scaled value from `variables`.

This only reproduces on native apps because mWeb is out of scope for this issue, and the bug depends on native `PixelRatio.getFontScale()` values at maximum accessibility settings. A later QA pass on different hardware (iPhone 13 / Samsung S23FE, v9.4.45-9) did not reproduce — likely because the fix shipped in #97281 and/or those devices hit slightly different font-scale caps — but the underlying style cascade bug was real on the originally reported devices.

### What changes do you think we should make in order to solve the problem?

Scope the fix to the Search Router Spend tag only, keeping `TextWithIconCell`'s existing defaults for transaction-table Tag/Category cells.

**1. Make the icon size configurable in `TextWithIconCell` (default stays 12 for existing callers):**

+    iconSize?: number;

Because `textStyle` is applied last in the style array, appending `styles.label` overrides `textMicro`'s `lineHeightSmall` without changing Tag/Category narrow-layout usages that intentionally pass `[styles.textMicro, styles.mnh0]`.

Using `variables.fontSizeLabel` for `iconSize` follows the established accessibility pattern already used for typography (`getValueUsingPixelRatio(13, 19)`) instead of ad-hoc `PixelRatio` math, and keeps the icon visually aligned with the label text at every font scale.

**Blast radius:** Two production files plus a unit-test assertion on the Spend `rightElement` props. Transaction table cells, other Search Router rows, and web are unchanged.

### What alternative solutions did you explore? (Optional)

- **Remove `styles.textMicro` from `TextWithIconCell` globally** — rejected because Tag/Category narrow cells rely on the micro typography for table density.
- **Increase `numberOfLines` or add padding** — rejected as a symptom fix; the root issue is the mismatched line height, not wrapping.
- **Build a Search-Router-only label component** — rejected as unnecessary duplication when a scoped `textStyle` override and optional `iconSize` prop solve the problem with minimal surface area.
- **Scale the icon with raw `PixelRatio.getFontScale()`** — rejected because `variables.fontSizeLabel` already encapsulates the app's capped accessibility scaling convention.

### What specific scenarios should we cover in automated tests?

- Assert Spend navigation `rightElement` passes `iconSize: variables.fontSizeLabel` and uses `TextWithIconCell`.
- On a native test harness with `PixelRatio.getFontScale()` mocked to maximum, render a Spend suggestion row and assert the "Spend" label text is fully visible (no clipped descenders) and the icon dimensions match `variables.fontSizeLabel`.
- Regression: Tag/Category `TextWithIconCell` usages still default to a 12px icon and `textMicro` styling.
