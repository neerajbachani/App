## Proposal

### Please re-state the problem that we are trying to solve in this issue.

Per [internal clarification](https://github.com/Expensify/App/issues/97866#issuecomment-5205703955), the bug in scope is on the **report detail page**: an approved expense report that contains **only non-reimbursable** expenses shows **"No further action required!"** instead of giving the workspace admin a **Mark as paid** option to close the report out. Showing **View** (not Pay) for those reports on **Spend > Reports** is expected and is not part of this fix. The original report also described a reimbursed report lingering under the Approved filter; internal review found that specific customer case did not match that state, though a separate client-side filter bug exists (see alternatives).

### What is the root cause of that problem?

Mark-as-paid on the report detail page is decided by `isPrimaryPayAction` (render gate) and `canIOUBePaid` (settlement options/label in `PayPrimaryAction`). Both treat "mark as paid" as a **reimbursement** action and reject non-reimbursable-only reports through three stacked gates.

**Gate 1 — payer check never uses the pay-elsewhere path on the detail page.**

`isPrimaryPayAction` always asks `isPayer` with `onlyShowPayElsewhere` hardcoded to `false`, and `canPayReport` only adds a non-payer admin fallback for **manual** reimbursement workspaces:

On a workspace with direct/electronic reimbursement (`REIMBURSEMENT_YES`) and a designated reimburser, `isPayer(..., false)` returns `true` only for that reimburser (or a bank-account sharee). This matches the repro precondition noted in the thread (workspace connected to a bank account; admin is not the payer).

### What changes do you think we should make in order to solve the problem?

Treat mark-as-paid on a **non-reimbursable-only** report as a bookkeeping status change, not a reimbursement, and stop gating it on reimbursement settings or designated-payer rules. Electronic pay (`onlyShowPayElsewhere === false`) stays unchanged.

**1. `src/libs/ReportPrimaryActionUtils.ts` — derive the case once and use it for both payer and payments gates.**

```ts
const {reimbursableSpend, nonReimbursableSpend} = getMoneyRequestSpendBreakdown(report);
const isOnlyNonReimbursable =
    reimbursableSpend === 0 && nonReimbursableSpend !== 0 && hasOnlyNonReimbursableTransactions(report?.reportID, reportTransactions);

const isReportPayer = isPayer(currentUserAccountID, currentUserLogin, report, bankAccountList, policy, isOnlyNonReimbursable);
const canPayReport =
    isReportPayer ||
    (canNonPayerAdminPay &&
        isOnlyNonReimbursable &&
        canMemberWrite(policy, currentUserLogin, CONST.POLICY.POLICY_FEATURE.WORKFLOWS_PAYMENTS)) ||
    (canNonPayerAdminPay &&
        policy?.reimbursementChoice === CONST.POLICY.REIMBURSEMENT_CHOICES.REIMBURSEMENT_MANUAL &&
        canMemberWrite(policy, currentUserLogin, CONST.POLICY.POLICY_FEATURE.WORKFLOWS_PAYMENTS));

// ...

    canPayReport &&
    isExpenseReport &&
    (arePaymentsEnabled || isOnlyNonReimbursable) &&
    isReportFinished &&
```

Passing `isOnlyNonReimbursable` into `isPayer` activates the existing pay-elsewhere admin carve-out for `REIMBURSEMENT_NO` policies (lines 2874–2876 in `ReportUtils.ts`). The new `canMemberWrite` branch covers direct-reimbursement workspaces where the viewing admin is not the designated reimburser.

### What alternative solutions did you explore? (Optional)

- **Wait for PR #95925 only.** That PR broadens admin payability for reimbursable reports but does not exempt non-reimbursable-only mark-as-paid from `arePaymentsEnabled`, the `REIMBURSEMENT_NO` Approved-status gate, or the Next Steps banner override. It would not fully fix the clarified bug on its own.
- **Broaden `canPay` for all mark-as-paid on direct-reimbursement workspaces** (dilshodmackbook-sketch's approach). Rejected here as too wide for this issue: it would also unlock mark-as-paid for reimbursable approved reports viewed by non-payer admins, which belongs in #95750 and must stay separate from the non-reimbursable-only bookkeeping case.
- **Fix the Approved-filter staleness in `getReportSections`.** There is a real client bug — status re-check runs only when `currentQueryJSON.type === expense`, but Spend > Reports uses `expense-report`, so `shouldShow` is always `true`:

  A one-line fix (`shouldShow = !isActionLoading ? isEligibleForStatus(...) : true`) would drop reimbursed rows from `status:approved` once live `statusNum` updates (and explain PAID→View on stale rows). Internal review found the **customer's** filter symptom did not match that state; the paginated-search repro is better tracked as a separate issue. I would not bundle it here to keep this PR focused on the report-detail mark-as-paid gap.
- **Refetch Search on every out-of-band status change.** Heavier and slower than applying the existing `isEligibleForStatus` predicate at render time; unnecessary for the report-detail bug.

### What specific scenarios should we cover in automated tests?

- Approved expense report with **only non-reimbursable** expenses, workspace admin who is **not** the designated reimburser on a `REIMBURSEMENT_YES` policy → `isPrimaryPayAction(..., canNonPayerAdminPay: true)` returns `true`; `canIOUBePaid(..., onlyShowPayElsewhere: true)` returns `true` while `canIOUBePaid(..., false)` stays `false`.
- Same report on a `REIMBURSEMENT_NO` policy at **Approved** status → `canIOUBePaid(..., onlyShowPayElsewhere: true)` returns `true` (currently false because of the SUBMITTED-only gate).
- `getReportNextStep` for an approved non-reimbursable-only report → does **not** return `NO_FURTHER_ACTION`.
- Regression: reimbursable approved report, non-payer admin on direct-reimbursement workspace → still no Pay (unchanged; covered by #95750).
- Regression: Search `getReportSections` row for non-reimbursable-only report → Pay action remains excluded via `shouldHidePayAsPrimaryAction`.
